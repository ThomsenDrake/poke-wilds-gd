# Menu And Save

## Supported behavior

- Pressing `Enter` opens the start menu while the player is not in battle.
- The start menu lists `POKEMON`, `BAG`, `SAVE`, `NEW GAME`, and `CLOSE`.
- Menu entries also accept a LEFT-CLICK (the start menu, the campfire craft menu, AND the storage screen wire `ItemList.item_clicked` to select + activate the clicked row). The mouse is a documented convenience, not a first-class input scheme — keyboard remains the canonical map ([bootstrap-and-overworld.md](bootstrap-and-overworld.md) § Input map). The storage screen's click route is the one gated surface: a click on the still-visible action list during a pending RELEASE confirm cannot mutate the box (`storage_screen.gd`'s `_on_entry_clicked` confirm gate — see [storage-and-party.md](storage-and-party.md)).
- The party screen lists party members with level, HP bar, and status abbreviation. Selecting a member offers `SWAP LEAD`, a `SUMMARY` panel (types, stats, moves with PP, EXP to next level), an eligible `FIELD MOVE` action, and `CANCEL`. When the campsite hold is non-empty and the party has room, the screen also offers a `RETRIEVE` action that pulls the oldest campsite-held Pokemon into the party and emits a `mon_retrieved` trace. Since Phase 3 the screen also offers `MOVE` (arbitrary reorder: up/down move the member live, `Z` commits, `X` restores the pre-move order via `set_party_order`; `set_party_lead` delegates to `move_party_member`) and — only when a storage box stands adjacent to the player — a `DEPOSIT` action that places the selected mon into the nearest box (`deposit_to_nearest`; storage boxes are MANUAL containers, never an auto-sink); deposit refusals (`last_party_member`, `would_strand_demolition` — the dynamic demolition-witness guard) flash in the screen's Hint label. Full storage behavior in [storage-and-party.md](storage-and-party.md).
- A field move action appears for species-flag-eligible moves (flag == 1; verified counts across all 952 `wilds_data.asm` files: HEADBUTT 57, RIDE 32, FLY 30, CUT 10, SURF 6, FLASH 6, DIG 2, SMASH 2, POWER 1, PAINT 1; BUILD 0). Choosing one closes the menu. The rendered entries are CAPABILITY DISPLAY: only the harvest actions (Cut/Dig/Smash) resolve the harvest on the faced tile with that Pokemon ("X can't use that here." on failure); any other move (HEADBUTT, RIDE, FLY, SURF, FLASH, PAINT, POWER) surfaces a display-only message ("X knows Y, but there's nothing here that needs it.") instead of silently harvesting — those moves' overworld triggers are future phases (HEADBUTT trees, RIDE mounts, FLY travel, SURF water traversal, PAINT recolor, POWER plants; Flash's passive Fire-type light READ is already live — see [camping-crafting-survival.md](camping-crafting-survival.md) § Night danger). BUILD never renders (0 species carry the flag; the live build path is overworld `Z` — see [building-and-placement.md](building-and-placement.md)). Overworld `Z` resolves with any capable party member. See [harvest-and-mutation.md](harvest-and-mutation.md). (The controls audit's per-move counts 25/15/12/5/4/1 used a different denominator; the inert MOVE SET matches exactly.)
- The bag screen lists items with display names, counts, and descriptions. A Potion can be used on a chosen party member to heal 20 HP; since Phase 5 the EVOLUTION STONES (fire/water/thunderstone/leaf/moon/sun/ice/dawn/dusk/shiny — an explicit id set) open the same party picker and confirm through `GameRuntime.use_stone_on_mon` (`stone_evolution_runtime.gd`): a successful evolution consumes the stone, preserves `is_shiny`, and traces `evolution_stone_used`; a no-effect target shows "It would have no effect." and consumes nothing (the Potion precedent; Eggs are refused). Stones are obtainable in the world — Dig bonus pools (the faithful Beach-Dig Water Stone plus flagged port-addition biome pools) and a happy Steel-type's shiny_stone cadence drop — and usable from the bag here; Ice/Dawn Stones stay scenario-grant-only (SNOW isn't diggable). See [breeding-shinies-drops-fishing.md](breeding-shinies-drops-fishing.md) § Evolution stones. Otherwise unusable items report that they cannot be used here (incl. fishing rods — the overworld Z is the only fishing trigger). Since Phase 2 the SLEEPING BAG is usable from the bag (`_activate_item` branch): a reusable key item (never consumed) that rests the party — every member heals `ceil(max_hp * 0.5)` and fainted members revive to 50% HP, with NO status cure (faithful: the bag revives but does not cure live status — beds are the resting cure), the clock advances (night rest → the next 07:00, day rest → +4h), and resting ESTABLISHES the campsite anchor (`campsite_tile = player_tile`; traces `rested` + `campsite_established`). Heal logic lives in `camping_runtime.gd` (subsystem `camping_loop`), mutating the party dicts directly in the `_apply_potion` pattern; the bed's interact-rest and the full heal/cure model are in [camping-crafting-survival.md](camping-crafting-survival.md).
- Save writes the current runtime state to `user://godot_port_save.json` in save schema v4 (party, bag, time of day, total steps, world overrides from harvesting, the campsite hold — anchor tile plus held Pokemon — placed structures from the building loop, and since Phase 3 per-placement storage-box `contents` — each box an INDEPENDENT container keyed by its tile, and since Phase 5 the breeding pen state `pastures` — pen anchors ("x,y") mapping to penned mons + ground eggs, validation owned by `breeding_runtime.apply_save_state`; see [breeding-shinies-drops-fishing.md](breeding-shinies-drops-fishing.md)). Placed structures ride the same additive pattern as the campsite hold: `SAVE_VERSION` stays 3, the clears (`world_overrides`) and placements (`structures`) are stored as two independent keys (a tile can be cleared and then built on, and future demolition must revert it to cleared ground, not respawn the tree), and saves from before building simply lack the `structures` key and backfill to empty on load. Phase 2 (camping/crafting) stays ENTIRELY v3-additive on these same keys — no version bump, no new top-level key: an extinguished campfire carries an extra `"lit": false` field on its placement ENTRY (absent = lit, so Phase-1 campfire saves load lit for free; `WorldOverrides.is_valid_placement` checks only kind + structure_id, so the extra key round-trips validate/normalize/merge/save untouched and a corrupt value is harmless — anything not-false reads as lit); the sleeping bag rides the existing `"bag"` key via `STARTING_BAG` (reusable — the count never decrements); rest just WRITES the already-persisted `campsite_x`/`campsite_y`/`time_of_day_minutes` vars; and recipes carry NO state at all (all campfire recipes are always available — the wiki has no discovery mechanic, so the craft menu is a pure function of recipes + bag counts, with nothing to migrate). Phase 3 (storage boxes) takes the PURELY ADDITIVE bump the building spec pre-pinned: `SAVE_VERSION` is now 4 and a storage box's placement entry gains a `contents` array (ABSENT = empty box — mons are the exact party/campsite mon shape); no key is renamed or dropped, so the bump's only behavioral effect is that a v3 build refuses a v4 save non-destructively to `.newer.bak` rather than loading box semantics it has no UI for (full schema, migration, and load normalization in [storage-and-party.md](storage-and-party.md) § Persistence). `save_migration` gains the v4 fixture (a storage box carrying `contents` round-trips; a contents-less v3 box backfills to empty); the v3→v3 additive fields are covered by `camp_survival`'s round-trip (extinguish → save → load → entry still carries `lit: false`) and `craft_flow`'s round-trip (crafted counts survive). See [camping-crafting-survival.md](camping-crafting-survival.md) § Persistence. Writes are ATOMIC: the payload is written to a `.tmp` file and renamed over the live save, so a crash mid-write leaves the previous save intact; a failed rename emits a `warning` and keeps the old file. On load, a corrupt save is parsed QUIETLY (`JSON.new().parse` returns an error code; the engine prints nothing on failure, so a handled refusal emits no spurious engine "ERROR: Parse JSON failed" line), preserved to `.corrupt.bak`, and a fresh start is recovered with a `save_recovery` trace (never silently); an absent save recovers the same way at event tier. A save whose `version` is newer than supported is REFUSED non-destructively: the file is renamed to `.newer.bak` and a `warning` fires BEFORE the runtime starts fresh, so the per-step autosave can never overwrite the newer save. v1/v2/v3 saves migrate on load (additive backfill: v1/v2 drop the legacy `unlocked_field_moves` key; v3→v4 backfills an absent `contents` to an empty box, and `_normalize_structures` sanitizes a corrupt `contents` to an empty box — never a crash or a torn entry).
- The runtime exposes a smoke-only determinism seam, `seed_for_smoke(seed)`, which pins BOTH the encounter rng and the battle rng so a scenario's audited inputs are a pure function of (code, save, seed) — the house seeding convention (`nav_audit`'s battle half calls it with `NAV_AUDIT_SEED`; `visual_sweep`/`display_matrix` pin `battle_runtime._rng` directly; `playtest_soak` pins its bot). Real play never calls it: `_ready` still wall-clock-randomizes both generators (miss-002).
- Runtime audio is two services: the music router (biome and battle tracks) and the cry player (species cries keyed by dex number at battle start and on faint, with a warning trace for missing files).
- New Game is confirm-gated: choosing `NEW GAME` opens a message-box confirm (`Z` yes / `X` no). Confirming resets the session with a new world seed, a starter Pokemon, a starting bag (5 Poke Balls, 3 Potions, and since Phase 2 1 Sleeping Bag — a reusable key item, faithful: "This item is in your bag at the start of the game"), and the clock at 10:00, then CLOSES the menu; cancelling leaves the menu open. The reset (and its save wipe) is never applied without an explicit confirm.
- Closing the menu emits a save and returns control to overworld movement.
- Transient message boxes yield to battle presentation instead of stacking over the combat UI.

## Smoke validation

- `menu_save` opens the menu and drives the New Game confirm flow on both branches — cancel leaves the confirm box down, the menu open, and the existing save intact (no `session_created` since the cursor), and confirming starts a new game (`session_created`) and closes the menu. The SAVE-entry save-on-close path is exercised by `playtest_journey`, not this scenario.
- `field_move` finds a `cut`-gated tile, drives the party-capability field-move flow (species flags + type auto-ability; there is no stored unlock state), and confirms the tile becomes walkable with the `field_move_used` trace.
- `save_migration` writes v1 and v2 fixtures plus a future-version fixture to the live save path (inside the runner's backup/restore guard) and drives the runtime's real load path: it asserts v1→v3 and v2→v3 field migration (legacy item id remap, dropped `unlocked_field_moves`, backfilled stats/fields) plus the additive v3→v4 storage-box contents bump, the non-destructive refusal of the future version (empty payload, `.newer.bak` preserved with its contents intact, version-refusal `warning`), a v3 fixture carrying a wall + a door under the additive `structures` key (asserting both round-trip into the generator's placement map while a structures-less v3 save backfills to empty), a v4 fixture carrying a storage box with `contents` (asserting the v3→v4 contents round-trip and load normalization while a contents-less v3 box backfills to an empty box), and emits `save_migration_passed` (payload carries `v4_ok`); it cleans up its `.newer.bak`/`.corrupt.bak`/`.tmp` artifacts so no fixture state leaks into sibling scenarios. `save_recovery` covers the corrupt/absent recovery path.
- `ui_render_audit` covers the start menu, party, and bag screens against the art-anchored render model.
