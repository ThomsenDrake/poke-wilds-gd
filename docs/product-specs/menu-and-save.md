# Menu And Save

## Supported behavior

- The playtest-feedback snapshot reads the current in-memory save payload through a
  read-only service invoked by the app controller; it adds no runtime child, never
  calls the save store, and never overwrites the player's live save. Its separate
  outbox owner atomically publishes the ZIP before the metadata commit marker, so
  retry cannot observe a torn pair. See [playtest-feedback.md](playtest-feedback.md).
- Oversized current-session traces retain complete JSONL records around an explicit
  truncation marker. That synthetic record carries the same `event`, `ts_msec`,
  `source`, and `payload` fields as every emitted runtime trace, so strict consumers
  can continue parsing a feedback bundle after the gap.

- The start menu lists `POKEMON`, `BAG`, `SAVE`, `OPTIONS`, `NEW GAME`, and `CLOSE` (the `OPTIONS` entry, index 3, opens the Options submenu below).
- The start menu's `OPTIONS` entry opens the Options submenu (`scripts/ui/options_screen.gd` + `scenes/ui/OptionsScreen.tscn`, a StartMenu child instance like the party/bag screens — `main.gd` gets zero lines). It configures the random-encounter opt-in ([overworld-pokemon.md](overworld-pokemon.md) § Configurable encounters): a `WILD ENCOUNTERS` row cycles `OFF (contact only)` → `CLASSIC (encounter tiles)` → `ANYWHERE (any tile)` (Z or ←/→), an `ENCOUNTER RATE` row nudges the per-step chance along the 0.02–0.50 ladder (←/→; greyed while encounters are off), and `BACK`. The session is the single source (`get/set_encounter_settings`; the mode/rate constants ride `SessionState`, single-sourced); every change writes through to the session at once (effective immediately) and is persisted by ONE save when the submenu closes (a save-per-nudge would write a full save per 2% step while scrubbing the rate), so the choice outlives the menu and the session. Default is `OFF` — wild battles come only from a shared-tile sprite collision until the player opts in.

- Save writes the current runtime state to `user://godot_port_save.json` in save schema v6 (infinite-world slice 1 RETIRED the v5 world-identity keys `root_seed`/`active_chain`/`chained_worlds` with world chaining — v4's fifteen payload keys UNCHANGED, `landmark_state` back on its top-level v4 seat now keyed per-instance `"id@x,y"` (slice 3), and a chain-less v5 save flattens losslessly on load — delta == `{version: 6}`; a truly chained v5 save is refused non-destructively to `.chained.bak` and a fresh start recovered — the Build 3 paragraph below is the HISTORICAL v5 record) — (party, bag, time of day, total steps, world overrides from harvesting, the campsite hold — anchor tile plus held Pokemon — placed structures from the building loop, and since Phase 3 per-placement storage-box `contents` — each box an INDEPENDENT container keyed by its tile, and since Phase 5 the breeding pen state `pastures` — pen anchors ("x,y") mapping to penned mons + ground eggs, validation owned by `breeding_runtime.apply_save_state`; see [breeding-shinies-drops-fishing.md](breeding-shinies-drops-fishing.md)). Placed structures ride the same additive pattern as the campsite hold: `SAVE_VERSION` stays 3, the clears (`world_overrides`) and placements (`structures`) are stored as two independent keys (a tile can be cleared and then built on, and future demolition must revert it to cleared ground, not respawn the tree), and saves from before building simply lack the `structures` key and backfill to empty on load. Phase 2 (camping/crafting) stays ENTIRELY v3-additive on these same keys — no version bump, no new top-level key: an extinguished campfire carries an extra `"lit": false` field on its placement ENTRY (absent = lit, so Phase-1 campfire saves load lit for free; `WorldOverrides.is_valid_placement` checks only kind + structure_id, so the extra key round-trips validate/normalize/merge/save untouched and a corrupt value is harmless — anything not-false reads as lit); the sleeping bag rides the existing `"bag"` key via `STARTING_BAG` (reusable — the count never decrements); rest just WRITES the already-persisted `campsite_x`/`campsite_y`/`time_of_day_minutes` vars; and recipes carry NO state at all (all campfire recipes are always available — the wiki has no discovery mechanic, so the craft menu is a pure function of recipes + bag counts, with nothing to migrate). Phase 3 (storage boxes) takes the PURELY ADDITIVE bump the building spec pre-pinned: `SAVE_VERSION` is now 4 and a storage box's placement entry gains a `contents` array (ABSENT = empty box — mons are the exact party/campsite mon shape); no key is renamed or dropped, so the bump's only behavioral effect is that a v3 build refuses a v4 save non-destructively to `.newer.bak` rather than loading box semantics it has no UI for (full schema, migration, and load normalization in [storage-and-party.md](storage-and-party.md) § Persistence). `save_migration` gains the v4 fixture (a storage box carrying `contents` round-trips; a contents-less v3 box backfills to empty); the v3→v3 additive fields are covered by `camp_survival`'s round-trip (extinguish → save → load → entry still carries `lit: false`) and `craft_flow`'s round-trip (crafted counts survive). See [camping-crafting-survival.md](camping-crafting-survival.md) § Persistence. Writes are ATOMIC: the payload is written to a `.tmp` file and renamed over the live save, so a crash mid-write leaves the previous save intact; a failed rename emits a `warning` and keeps the old file. On load, a corrupt save is parsed QUIETLY (`JSON.new().parse` returns an error code; the engine prints nothing on failure, so a handled refusal emits no spurious engine "ERROR: Parse JSON failed" line), preserved to `.corrupt.bak`, and a fresh start is recovered with a `save_recovery` trace (never silently); an absent save recovers the same way at event tier. A save whose `version` is newer than supported is REFUSED non-destructively: the file is renamed to `.newer.bak` and a `warning` fires BEFORE the runtime starts fresh, so the per-step autosave can never overwrite the newer save. v1/v2/v3 saves migrate on load (additive backfill: v1/v2 drop the legacy `unlocked_field_moves` key; v3→v4 backfills an absent `contents` to an empty box, and `_normalize_structures` sanitizes a corrupt `contents` to an empty box — never a crash or a torn entry). v4 saves (and version-less ones — the frozen golden fixture carries NO `version` key) migrate to v5 on load via the PURE `scripts/domain/save_migration.gd` transform (`root_seed` backfills from `world_seed`, `active_chain` to `"0,0"`, `chained_worlds` to `{}`; a top-level `landmark_state`, when present, relocates BYTE-VERBATIM into `chained_worlds["0,0"].landmark_state` and the v4 top-level seat drops — the single v4 field that moves; the golden carries none, so its byte-proof delta is exactly the three identity keys). **Creation identity (new-game flow slice):** three further ADDITIVE v6 keys carry the creation choices — `player_name` (default `"PLAYER"`), `player_avatar` (default `"ben"` — the pre-slice hardcoded sheet), `shiny_rate` (default `256`) — marshalled by `session_payload.gd` write-only-when-non-default (session_payload.gd:62-67) with load normalizers (uppercase A-Z ≤8 / sheet-missing tolerated by the frame-builder fallback / snap to the shiny ladder; session_payload.gd:135-148). NO `SAVE_VERSION` bump — the additive-after-v2 rule, quoted from the `encounter_settings` precedent (§ Configurable encounters): "the setting persists across new games within a session as a player preference — `reset_for_new_game` deliberately does NOT clear it." The creation identity rides that exact contract: it persists across the pause-menu reset (`main._on_game_reset` re-applies the avatar), a default-identity save carries none of the three keys, and the frozen golden fixtures stay byte-identical.
