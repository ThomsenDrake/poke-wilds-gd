# Storage And Party

Phase 3 fills the last Phase-1 placeholder: the Storage Box becomes an interactive Pokemon container, and the party screen grows real management (arbitrary reorder + deposit). Storage boxes are craftable STRUCTURES that ride the Phase-1 placement system (definition, 2 Log cost, occupancy, and the demolition contract all live in [building-and-placement.md](building-and-placement.md)); their CONTENTS and the deposit/withdraw/release flows live here. The runtime is `scripts/runtime/storage_runtime.gd` (RefCounted, the `build_runtime.setup` shape); the UI is `scripts/ui/storage_screen.gd` + `scenes/ui/StorageScreen.tscn` (ui-references-only, self-wired through the `/root/GameRuntime` convention like the camp menu). Every decision below is sourced: `.firecrawl/buildings-scrape.md:290-294` (Storage Box = 2x Log; "store, release, and nickname"; "Unlike the mainline games, the contents of the box are not shared with other built boxes"), `.firecrawl/house-building-scrape.md:261` (boxes kept outside/right next to an entrance; caught mons stack in homes until moved; never block the path to your box), `.firecrawl/house-building-scrape.md:234` + `.firecrawl/pokewilds-getting-started.md:76` (overflow captures are confined to the house = last slept place), `.firecrawl/pokewilds-build.md:37-38` (storage "acts as a PC for Pokemon, but is not connected to other storage chests"; a filled chest cannot be Cut), and `.firecrawl/lchan-review.md:45` (release = "drop" a Pokemon; "no guarantee a dropped Pokemon will stick around").

## Supported behavior

- A Storage Box is placed like any other structure (Fighting-type Build capability, 2 `log` — `structures.IDS` + `cost_for`, see [building-and-placement.md](building-and-placement.md) § Structures and costs). It is solid (blocks movement) and interactable. The original keeps boxes outside/right next to an entrance (`.firecrawl/house-building-scrape.md:261`); that is player discipline, NOT an enforced placement rule — the port places a box on any walkable faced tile like every other structure.
- Each box is an INDEPENDENT, NON-SHARED container: box identity IS its placement tile, there is no global box store, so two boxes can never share contents BY CONSTRUCTION (faithful: "the contents of the box are not shared with other built boxes", `.firecrawl/buildings-scrape.md:294`; "acts as a PC for Pokemon, but is not connected to other storage chests", `.firecrawl/pokewilds-build.md:37`). There is deliberately no shared-PC abstraction.
- Overworld context `Z` on a placed box opens the storage screen (LANDED — the campfire-menu pattern): `field_action_router._route_camp_object` matches `storage_box` (the `BOX_ID` arm), disables player input, and `open_screen(tile)` runs; the screen's `closed` signal re-enables input and saves (every box mutation persists), mirroring the CampMenu route. The closing `X` press feeds `input_router`'s GENERALIZED same-frame latch (wired by `main.gd`'s `bind_ui_consumers`; see [bootstrap-and-overworld.md](bootstrap-and-overworld.md) § Input map), which covers the StorageScreen alongside the CampMenu, StartMenu, and MessageBox, so it cannot re-fire the polls; `field_action_router._overlay_open` (the registry-mandated name covering BOTH overlays) plus the StorageScreen visibility now carried in `main.gd`'s `overworld_idle` and `_toggle_menu` neutralize the polls while the screen owns the input. `storage_runtime.open_box` traces `box_opened {tile, count}` on open, and `storage_flow` drives the box loop through this real Z seam (the router disables the avatar on open and the `closed` handler re-enables it — the `set_battle` poll-gate workaround is gone).
- The storage screen shows two columns — the BOX contents and the PARTY (n/6) — with per-row actions. Box side: `WITHDRAW`, `RELEASE`, `SUMMARY`, `CANCEL`. Party side: `DEPOSIT`, `SUMMARY`, `CANCEL`. Rows reuse the party-screen row builder (ui→ui only).
- DEPOSIT moves a party mon into the faced box; WITHDRAW moves a boxed mon into the party. Both are MANUAL — the original's boxes are walked-to containers the player manages by hand (`.firecrawl/house-building-scrape.md:261`), never an auto-routing sink.
- RELEASE removes a mon permanently and is CONFIRM-GATED at the UI layer: choosing `RELEASE` opens the MessageBox sibling confirm (the New Game precedent — the 0.2 contract: never add a destructive action without a confirm), the cancel branch returns to the actions, and the confirm branch executes the runtime release. The confirm wording double-emphasizes permanence ("It will be gone for good.") because the port's release is permanent removal (documented deviation below). The runtime executes releases confirm-agnostic, exactly like `new_game` — confirmation is UI-owned.
- Refusals are traced, never silent: every refused deposit/withdraw/release emits `storage_refused {action, tile, reason, species_id}` — `no_box` (no storage box at the tile), `no_such_mon` (index out of range), `last_party_member` ("You can't deposit your last Pokemon." — party size 1), `party_full` (withdraw at party size 6), or `would_strand_demolition` (the witness guard below). (Infinite-world slice 2 hardening: `storage_flow` clears pre-existing placements at setup — the witness dormancy math assumes only its own structures stand; a polluted boot save's way-stone (SAND shell ⇒ Smash) would otherwise join the guard's required set. The per-scenario save guard restores afterwards.)
- A NON-EMPTY box refuses demolition: `build_runtime.try_demolish` resolves `structure_id == "storage_box"`, and if the entry's contents are non-empty it refuses `demolish_refused {structure_id, tile, reason: box_not_empty}` ("The storage box isn't empty. Take your Pokemon out first.") BEFORE removing anything — refund untouched, placement and contents intact (faithful: a filled chest cannot be Cut, `.firecrawl/pokewilds-build.md:38`). The original's rule spans same-tile chests on upper/lower floors; the single-floor port reduces it to this per-box check. An EMPTY box Cuts normally through the existing demolition path (full 2 Log refund, `structure_demolished` + `materials_refunded`), and because contents live ON the placement entry, demolition of an empty box removes entry + (empty) contents atomically — there is no orphan-contents path.
- Party screen: ARBITRARY REORDER replaces the swap-lead-only limitation — `MOVE` enters a reorder state where up/down move the member live (`session_state.move_party_member`, row rebuilt each step), `Z` commits, `X` restores the pre-move order (`session_state.set_party_order` snapshot); `set_party_lead` delegates to `move_party_member(from, 0)` (existing callers unchanged). DEPOSIT is offered only when an adjacent box exists (`storage_runtime.box_tile_near` — a deterministic UP/DOWN/LEFT/RIGHT scan for the first storage box next to the player, the "right next to an entrance" rule mechanized; it returns `{found, tile}` and the `found` flag — never a tile sentinel — gates the entry, so a box built at world tile (0,0) offers DEPOSIT like any other box); it deposits the selected mon to that box (`deposit_to_nearest`). Refusals flash in the screen's existing Hint label (no new toast wiring). The campsite-hold `RETRIEVE` action is unchanged ([menu-and-save.md](menu-and-save.md)).
- OVERFLOW POLICY (decision, no change): full-party captures still relocate to the CAMPSITE HOLD (`battle_runtime` → `mon_relocated`, retrievable via `RETRIEVE`). Boxes are never an overflow sink. Rationale: (1) faithful — the original confines overflow mons to the last slept place (`.firecrawl/pokewilds-getting-started.md:76`, `.firecrawl/house-building-scrape.md:234`), and boxes are manual walk-to containers; (2) the NO-LOSS exit criterion — the campsite anchor ALWAYS exists (it defaults to spawn before the first rest), while a box may not exist yet, may be distant, and "nearest box" routing would invent spatial logic the original lacks and can fail — the hold cannot fail; (3) auto-routing would make boxes a shared-PC-like abstraction, contradicting sourced box independence; (4) `battle_runtime.gd` stays untouched — zero regression risk to the 0.1 non-losing path. The player's path from hold to box is RETRIEVE then DEPOSIT beside a box. `storage_flow` proves the no-routing policy (full-party capture → campsite hold, never a box).
- CAP POLICY (decisions): NO per-box mon cap — faithful, mons "stack on top of one-another... until they're moved" with no number in the source (`.firecrawl/house-building-scrape.md:261`); a cap would invent a refusal the original lacks. Save size is bounded by total mons caught (gameplay-bounded); if soak ever shows a payload problem, add a traced soft WARNING, never a refusal (documented assumption). Box count shares the existing 10k clears+placements override cap (`world_overrides.MAX_OVERRIDES`) — no new cap. Party cap stays 6 (withdraw refuses `party_full`).
- Nickname support (`.firecrawl/buildings-scrape.md:294`) is a DOCUMENTED DEFERRAL: mons already carry a `name` field that survives deposit/withdraw round-trips, so a future RENAME entry is purely additive (tech-debt-tracker).

### The demolition-witness guard extension (load-bearing)

The building spec's load-bearing invariant ([building-and-placement.md](building-and-placement.md) § The would-trap guard) says a region-scale enclosure stays escapable because the party that gathered the materials to build can always demolish — which held while "mons never leave the party". Boxes make mons LEAVE the party, so the guard extends DYNAMICALLY:

- `storage_runtime` computes the required witness moves by walking `placements_for_save()`: per placed tile, `Structures.demolish_move_for(structure_id, biome)` accumulates the move set the standing structures need (cut and/or smash).
- A deposit or a PARTY release that removes mon m from party P is refused `would_strand_demolition` ("You can't let X go — nothing left in your party can CUT, and you have structures standing.") when that set is non-empty and P carries a required move M but P-without-m does not.
- The PARTY pool counts, never box contents — the party travels with the player, while a box may be sealed away behind the player's own wall ring, so counting it would be unsound (conservative direction).
- Zero placed structures → the guard is dormant. Release FROM a box never changes the party pool → no guard there.
- The STATIC audit (`build_runtime.unwitnessed_demolish_moves()`) is unchanged — it is a cost-table property; `storage_flow` asserts the dynamic half (deposit the last Cut carrier with a wall standing → refused; demolish the wall → the same deposit proceeds). The O(placements) `get_tile_logic` walk per deposit/release is negligible (rare actions; documented).

## Persistence (save schema v4)

DECISION: save schema bumps v3→v4, PURELY ADDITIVE — the exact bump [building-and-placement.md](building-and-placement.md) § Persistence pre-pinned ("Phase 3 adds `contents` to box entries — THAT is the v3→v4 bump, which only works because `structures` already exists in v3"). `SessionState.SAVE_VERSION := 4`; no key renamed or dropped.

- Contents live as an additive field ON the placement entry, keyed by tile (the `"lit": false` campfire precedent — `structures.gd` / [camping-crafting-survival.md](camping-crafting-survival.md) § Persistence), never a parallel map, so a box and its contents cannot desync:
  ```
  structures["x,y"] = {"kind": "placed", "structure_id": "storage_box", "by": "build",
                       "step": int, "contents": [ <mon dict>, ... ]}   # ABSENT = empty
  ```
- Mons are the EXACT party/campsite mon shape (species_id, name, level, exp, max_hp, current_hp, status, sleep_turns, moves, stats); non-box placements never carry `contents`.
- WHY THE BUMP when `"lit"` stayed v3-additive: the plan mandates it, and it is the safe direction — a v3 build encountering a v4 save REFUSES non-destructively to `.newer.bak` (`save_store.gd`, the existing version-refusal ordering: preserve BEFORE the fresh-start autosave) instead of loading box semantics it has no UI for and then autosaving over them. v4 reads v3/v2/v1 saves exactly as today.
- Migration v3→v4 is additive backfill: an absent `contents` reads as `[]`; the v1/v2→v3 backfill chain (`session_state.apply_loaded_state`) is untouched.
- Load normalization: `session_state._normalize_structures` gains a contents sanitizer for storage_box entries (mirrors `_normalize_campsite`): a non-Array `contents` is erased; each element runs through `PokemonRules.normalize_loaded_mon`; non-dict elements are dropped. A corrupt contents value degrades to an EMPTY BOX, never to a crash or a torn entry — no Pokemon is lost to a parse edge; the mon dicts that survive normalization are exact.
- Round-trip guarantee with ZERO generator plumbing changes: `WorldOverrides.is_valid_placement` checks only kind + structure_id, so the extra key rides validate/normalize/merge/save untouched (the same guarantee `"lit"` rides); `to_save` / `merge_placements` already `duplicate(true)` whole entries, and contents ride `structures_overrides` through `session_state.to_save_payload` unchanged.
- Atomic writes unchanged: `save_store.gd` keeps the JSON.stringify → `.tmp` → POSIX-rename path and the corrupt/newer recovery; contents only grow the payload, and the torn-write recovery is shape-agnostic.

## Documented deviations

- RELEASE IS PERMANENT REMOVAL. The original "drops" a released mon into the world with "no guarantee a dropped Pokemon will stick around" (`.firecrawl/lchan-review.md:45`); the port has no overworld-mon entities until Phase 6, so release removes the mon permanently. The double-emphasized confirm wording is the compensation; overworld-drop release is tech debt for the overworld-mon phase.
- RELEASE-CONFIRM PRESENTATION is the shipped NEW GAME confirm's presentation, accepted as-is. The MessageBox is the EARLIEST `UI` sibling by design (`message_box.gd` header: StartMenu/StorageScreen/CampMenu are later siblings that gate their own input while a confirm is pending), so the StorageScreen's full-rect 0.5-alpha `Dim` draws ON TOP of the confirm panel — the "Release X? It will be gone for good." prompt is visible but dimmed to ~50% contrast, exactly as the already-shipped NEW GAME confirm sits behind the start-menu dim. This is a readability choice, not a correctness gap: BOTH confirm paths (keyboard Z/X and the action-list mouse click) are verified correct by `storage_flow`'s release branches and `storage_release_mouse_check` (the click is gated mid-confirm, so the prompt's only effect is the deliberate Z/Enter). A full-contrast fix (raising the MessageBox `z_index` above the menu dims, or reparenting the confirm to the top of the UI stack) is deferred as non-minimal — it would move the MessageBox above every menu/baseline state that captures it and risks the captured-baseline pixels for a cosmetic gain on a prompt whose behavior matches the shipped baseline. **RESOLVED by the GBC restyle (wave 2, § GBC stage restyle below):** the scene's full-rect `Dim` RETIRED with the stage rebuild, and the wave-1 MessageBox textbox band carries `z_index` over later `$UI` siblings, so the confirm now draws at full contrast over the screen — the deferred fix is moot.
- PARTY-RELEASE IS UNWIRED. `storage_runtime.release_from_party` (the `mon_released{source:"party"}` emitter, witness-guarded) is a runtime capability with NO wired UI caller — the storage screen releases from the BOX only and the party screen has no RELEASE entry, so the reachable `source` set today is `{"box"}`. Party-release waits on a party-screen entry (a future additive UI seam); until then the `"party"` source never fires in play.
- NICKNAME is deferred (above): the source lists "store, release, and nickname" (`.firecrawl/buildings-scrape.md:294`); store + release ship, rename is an additive future entry on mons that already carry names.
- OVERFLOW never routes to boxes (rationale in Supported behavior): campsite ground beats box, by decision, and `storage_flow` proves it.
- WORLD-GENERATOR REACH: `storage_runtime` writes contents through `world_gen.get("_placements")[tile]["contents"]` — the documented reach `field_action_router` already uses for the campfire `"lit"` toggle, because `scripts/domain/world_generator.gd` is at 318/320 with no room for a mutator; reads use the public `placements_for_save()`. Tech debt promotes the reach to typed accessors when world_generator next has budget.
