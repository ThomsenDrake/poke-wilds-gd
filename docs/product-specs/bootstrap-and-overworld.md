# Boot And Overworld

## Supported behavior

- The app boots into `res://scenes/app/Main.tscn`. Since the new-game flow slice the boot is SPLIT by who is booting: a scenario boot (a `.godot-smoke/scenario.json` request present) keeps the pre-slice path exactly and boots straight into the world; a PLAYER boot shows the startup splash, then the title screen, and never auto-starts a game or writes a save (§ Boot, splash, title, and creation below).
- The autoload runtime initializes source data, session state, and save state before the main scene starts normal play. On a player boot the initialization is LOAD-ONLY (`ensure_initialized(false)` — never `new_game`, never a save write); the silent-new-game behavior survives for scenario boots only.
- The overworld is rebuilt from the saved seed and centered on the saved player tile. On a player boot this happens only when CONTINUE or a confirmed creation enters the world (`_enter_world`); until then the title flow owns the screen and the player input stays disabled.
- The player moves on a 16x16 tile grid with continuous hold-to-move stepping and a faster run modifier on `X`, rendered from the source `ben-walking.png` / `ben-running.png` sprite sheets with direction-correct frames. Draw order is y-sorted: the player renders behind tall prop canopies when standing north of them and in front when standing south.
- Grass tiles can trigger wild encounters. Water, trees, cacti, swamp trees, rock cliffs, snow trees, and lava block movement.
- Entering battle clears transient overworld message UI before the battle screen appears, plays the wild species' cry, and switches to the battle theme; when the battle ends, the fainted side's cry sounds (victory or defeat) and the biome track resumes.
- When movement is blocked the player avatar surfaces a biome-specific reason from the world view (for example "A tall tree blocks the way.").
- Each completed step advances the session clock by one minute and the step counter by one; both persist in the save. The world view tints for time of day (night, dawn, dusk) via `set_time_of_day`. Since Phase 2 the day/night phase is GAMEPLAY, not just presentation: `scripts/domain/day_phase.gd` is the single source of truth (night = minutes >= 1230 or < 270; dawn/dusk/day all label `"DAY"`) MIRRORING the world view's `TIME_OF_DAY_KEYFRAMES` (the `night_cycle` scenario asserts the boundary minutes 269/270/1229/1230 agree with the keyframes, so the duplication cannot drift silently), and it drives the night-danger / nocturnal-spawn / time-evolution systems in [camping-crafting-survival.md](camping-crafting-survival.md). At night a static warm glow is composed inside `structure_layer.gd` around lit campfires/torches — a generated gradient texture with NO per-frame animation (night-only, refreshed on `world_overridden` and player tile change), so the visual sweep stays byte-stable; `world_view.gd` itself is untouched.
- The music router plays a biome-specific overworld track on boot and whenever the player crosses into a new biome, switches to the wild-battle theme during battle, and resumes the biome track afterward.

## Biomes and traversal

- The world is generated from a seeded elevation, moisture, and biome noise field.
- Biome selection is progressive: tiles near the origin favor plains and grassland; forests and savanna appear farther out; desert, swamp, and rock appear at greater distance; snow and lava appear deepest in the world. This makes rarer biomes harder to reach, matching the original exploration incentive.
- Biomes are defined in `scripts/domain/biome_defs.gd` as a pure data table: base texture, optional atlas region, encounter flag, walkability, block reason, and scatter props with their own block reasons.
- `world_generator.gd` picks a biome per tile and scatters biome props deterministically from the seed, then overrides high-elevation tiles with rock cliffs. Tile logic (`get_tile_logic`) is separated from texture loading (`get_tile`) so navigability and traversal probes run without touching the GPU.
- Traversal rules are data-driven: each blocked tile carries a human-readable `block_reason` with a hint and a `requires_field_move` key. Harvestable blockers (trees, cacti, swamp trees, snow trees, rock cliffs) open only by being cleared through harvesting; water opens passively while a surf-capable Pokemon is in the party. See [harvest-and-mutation.md](harvest-and-mutation.md).
- The world generator's sparse per-tile override map carries TWO independent entry kinds: the harvest "cleared/dug" facts (owned here) and, since the building slice, "placed" structures added by the `building_loop` subsystem (a documented cross-subsystem co-modification of `world_overrides.gd` / `world_generator.gd`; this spec and those files stay owned by `world_runtime`). Placements apply at the same single `get_tile_logic` boundary as clears, so a built wall/door/fence participates in traversal, render, and collision exactly like a world prop — occupancy agrees by construction. Placements persist under a separate additive v3 `structures` save key (the clears `world_overrides` key is untouched); see [building-and-placement.md](building-and-placement.md).
- `world_view.gd` exposes `get_tile_biome`, `get_traversal_block_reason`, `tile_requires_field_move`, `set_time_of_day`, and `validate_world_invariants` for the player avatar and field-move flows, and emits a `biome_entered` trace whenever the center tile crosses into a new biome. Its per-tile data cache (`_tile_cache`) is window-evicted on every `sync_visible` pass — tiles outside the visible window are dropped AFTER the inactive-node cleanup, never mid-pass — so the cache stays bounded to the visible window (about 61×41 tiles) instead of growing without bound as the player walks; transient off-window audit queries are reclaimed on the next per-step sync. Since Phase 2 the lit light-source glow is composed inside `structure_layer.gd` (the building loop's layer) rather than the world view — the design's documented fallback path, chosen so the camping visuals never depend on which compositor landed: one static generated gradient per lit campfire/torch in the visible window, night-only, refreshed on `world_overridden` (the campfire lit toggle mirrors that signal) and player tile change, so `world_view.gd` and `main.gd` stay untouched. See [camping-crafting-survival.md](camping-crafting-survival.md) § Light rendering.

## Navigable spawn

- `world_generator.find_walkable_spawn` searches outward from the origin in expanding rings and returns the first walkable tile that has at least two walkable neighbors and one non-encounter neighbor. New games spawn the player there instead of at `(0,0)`, which may be water or a blocked tile. **Beach preference (infinite-world slice 4):** the scan runs a beach FIRST pass — the first SAND (beach-band, elevation-driven) tile that is walkable in resolved logic and has a cardinal neighbor whose `requires_field_move == "surf"` (WATER), gated by the same `_spawn_meets_neighbors` (WATER is non-walkable, so a water-only sandbar is rejected and `SPAWN_REACH_MIN` reachability holds); only when no beach is within `SPAWN_SEARCH_RADIUS` does it fall back to the existing walkable scan byte-identical. Faithful "start on a beach"; deterministic (rng-free, `_ring_tiles` order, fixed direction order). Witnessed by `seed_choice` (beach spawn) and the re-pinned spawn-dependent baselines.
- `world_generator.reachable_walkable_count` performs a bounded flood fill from a start tile to prove the spawn is not walled off (optional `blocked` parameter treats one extra tile as unwalkable — the build trap guard's hypothetical stamp, so the guard never mutates the live placements map). `validate_invariants` asserts the spawn reaches at least `SPAWN_REACH_MIN` tiles within `SPAWN_REACH_BUDGET`.

## Biome-specific encounters

- `scripts/domain/biome_encounters.gd` builds encounter tables from the per-species `spawn_biomes` on the catalog entries. Catalog data provenance (since the PokeAPI catalog migration): `scripts/data/pokemon_catalog.gd` loads the GENERATED `assets/data/catalog/{species,moves,items}.json` — authored offline by `tools/import_pokeapi.py` from a pinned PokeAPI/api-data checkout, with the vendored tree's `wilds_data.asm` custom fields (spawn biomes included) carried forward at import time; the runtime no longer walks the `.asm` tree (see [../references/source-assets.md](../references/source-assets.md)). Source biome tokens that differ from world biome ids (for example `DEEP_FOREST` or `TIDAL_BEACH`) are mapped through `SOURCE_BIOME_ALIASES`; species carrying the source `TYPE` sentinel (or no spawn data) fall back to the type-based biome table (for example `FOREST` draws from `BUG`, `GRASS`, `POISON`, `FLYING`).
- Encounter eligibility requires battle-viable species: battle sprites, a catch rate, base stats, and a learnset. The literal `EGG` never spawns. Phase 7 ([world-depth.md](world-depth.md) § Legendaries) additionally bars the frozen seven (`LEGENDARY_IDS` — MEWTWO + the six Regis) from EVERY pool: they are static ring-≥60 stationary entities, never random encounters. No legendary has any `wilds_data.asm` spawn line, but they are battle-viable AND carry the `TYPE` sentinel, so the exclusion guards BOTH the type fallback AND the otherwise-unguarded full-catalog fallback (belt-and-suspenders beside the no-token fact); the roster is frozen in `scripts/domain/legendary_placement.gd`.
- In grass biomes (GRASSLAND, FOREST, SAVANNA) encounters are tied to visible tall-grass patches scattered deterministically by the generator; other encounter biomes keep biome-wide encounters. (Since the configurable-encounters slice this per-step random roll is OPT-IN and OFF by default — wild battles come only from a shared-tile sprite collision until the player enables it; [overworld-pokemon.md](overworld-pokemon.md) § Configurable encounters. The `encounter` tile flag + this eligibility model are unchanged; only whether the roll fires is gated.)
- `game_runtime.generate_wild_encounter` accepts an optional biome id and rolls from the filtered table. If no species match, the filter falls back to the full catalog and emits a `warning` trace so the escape hatch stays observable. If the catalog itself is empty, the encounter is skipped with a `warning` trace instead of fabricating a synthetic Pokemon.
- Since Phase 2 the filter gains a time-of-day dimension: `filter_species_ids(species_dict, biome, time_of_day := "DAY")` (the additive default kept the sole caller compiling until `game_runtime` passed the real `DayPhase.time_of_day_label`) excludes the one wiki-anchored night-only species (UMBREON, Savanna night) from DAY pools and extends every biome's NIGHT pool with the GHOST type (faithful: ghosts seek you out everywhere at night). Separately, `game_runtime._pick_encounter_species` delegates to the night system at night without light — half of those encounters become a battle-viable Ghost-type from a sorted type-derived pool (`night_hazard_spawned`), riding the existing shared `_rng` so `seed_for_smoke` pins the stream with no new seam. The level-from-distance and fallback-species helpers were extracted to `scripts/domain/encounter_selection.gd` to free the `game_runtime.gd` budget (same-line call-site edits only). Full contract in [camping-crafting-survival.md](camping-crafting-survival.md) § Night danger and § Nocturnal spawns.

## Input map

- Movement: arrow keys or `WASD`
- Confirm: `Z`
- Cancel (in menus/battle) / run modifier (in overworld): `X` — one physical key deliberately shared across two actions in mutually exclusive contexts. UI screens consume `action_b` via `_unhandled_input` only while visible; `run` is polled only during overworld movement (`is_action_pressed` while input is enabled). The contexts never overlap, so the shared key never collides (no rebind needed).
- Start menu: `Enter`
- Overworld context action: `Z` on the faced tile, in precedence order — camp-object interaction FIRST (`field_action_router._route_camp_object` reads the faced structure: a placed campfire opens the camp menu — Craft / Extinguish-or-Light / Demolish; a placed bed rests the party — see [camping-crafting-survival.md](camping-crafting-survival.md); a placed storage box opens the storage screen — see [storage-and-party.md](storage-and-party.md)); then harvest (Cut a tree → `log`, Smash a cliff → `hard_stone`, Dig ground → `dry_soil`; see [harvest-and-mutation.md](harvest-and-mutation.md)); then build mode on a walkable faced tile with a Build-capable (FIGHTING auto-type) party member (see [building-and-placement.md](building-and-placement.md)). While ANY router-opened overlay is visible (`field_action_router._overlay_open` — the camp menu OR the storage screen), the context route no-ops so `Z` stays owned by the overlay.
- Overlay ownership: while ANY input-phase overlay is open (the camp menu, the start menu, the storage screen, or a MessageBox confirm), `Z`/`X`/`Enter` BELONG to it (`_unhandled_input` during the input phase, which runs before the `_process` polls). A press that closes or confirms an overlay there must not also fire the same-frame polls, so a GENERALIZED same-frame latch in `input_router.gd` (`_ui_ate_press`, set via `bind_ui_consumers` AND by `main._on_battle_finished` via `note_press_consumed`) suppresses BOTH `poll_menu_toggle` and `poll_context_action`. `main.gd`'s `_ready` calls `bind_ui_consumers([$UI/CampMenu, _start_menu, _message_box, $UI/StorageScreen, $UI/TitleScreen, $UI/CreationScreen])`, connecting the ARGLESS `closed`/`confirmed`/`cancelled` signals of all six UIs to the latch (the argless contract is load-bearing — a producer that grew an argument would silently stop setting it; the new-game flow slice added the two title-flow screens, which emit argless `closed` on EVERY hide — § Boot, splash, title, and creation). One latch, set by every producer, consumed by both polls — this kills every same-press double-fire at the shared root: Enter no longer opens the start menu under a closing camp menu; Z-on-Demolish no longer re-fires harvest/build on the bare former campfire tile; a start-menu CLOSE no longer re-harvests the faced tile; a MessageBox NEW GAME confirm no longer harvests the spawn-facing tile on the brand-new world (superseding the "New game started." toast); and an inert party-screen FIELD MOVE no longer harvests the faced cut-tile its capability message just declined. The latch ALSO covers the one input-phase event that is not an overlay close/confirm: a press that ENDS A BATTLE. Z-on-RUN (`run_from_battle`) and a ball-select Z capture (`use_pokeball`) — the only SYNCHRONOUS end paths — resolve inside `battle_view._unhandled_input`, emitting `battle_finished` within the input phase (victory/defeat emit AFTER the turn animation, from `battle_turn_player`, with no press step); `main._on_battle_finished` re-enables the overworld there (`_in_battle = false` shares its line with the `note_press_consumed()` call — same-line edit, the 220-line budget), so the same-frame poll can no longer harvest/build the faced tile (pre-fix the harvest toast superseded "Got away safely!", or build mode opened on the faced tile). It is set UNCONDITIONALLY at the single `battle_finished` endpoint covering every path (RUN, capture, victory, defeat — the only end classes; any future press-driven end, e.g. a message advance if one lands, is covered by the same unconditional latch with no new wiring): the context poll resets the latch every frame, so a press-less animated end strands it for one frame — that frame's toggle poll ALSO early-returns once (a coincidental Enter loses one menu toggle) — and the press after it still fires. The latch is consumed by the context poll — `Main._process` calls the toggle poll FIRST and the context poll second, every frame (the order contract; the context poll captures + resets the latch unconditionally, so a toggle-only frame strands it for one harmless frame). The `input_gate` scenario drives the camp-menu races (parts A/B) plus the start-menu CLOSE, inert-FIELD-MOVE, and NEW-GAME-confirm leak paths (parts C/E/D in `input_gate_menu_checks.gd`) through real input injection (the shared `smoke_tap.gd`); the `battle_end_input` scenario drives the battle-end races the same way — a real Z on RUN and a real ball-select Z capture facing cut-harvestable tiles (no re-fire: the trees stand, the escape/capture toasts survive) PLUS the over-suppression guard (a fresh deliberate Z the next frame still harvests).
- Build mode (while active): movement keys cycle the selected structure, `Z` places, `X` exits.
